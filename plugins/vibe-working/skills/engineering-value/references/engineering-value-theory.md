# 工程收益理论

## 术语边界

“工程收益”是本项目用于开发范围决策的操作性术语。软件工程领域没有一个统一命名为“工程收益理论”的单一理论；它综合了价值导向软件工程、软件工程经济学、架构成本收益分析和不确定性决策。

本理论关心一项工程决策最终创造或保护了多少价值，以及为此承担了多少全生命周期成本和风险。价值可以表现为功能效果、质量、可靠性、安全性、交付速度、用户时间、维护能力或未来选择空间，不限于财务收入。

候选方案首先来自问题的因果结构和系统事实；行业方法用于提供经过实践检验的决策框架。第一性推导要说明目标、机制和必要条件，成熟方法要核对适用前提。方法名称、流程完整度和行业惯例本身不构成收益。

## 理论来源

### 1. 价值导向软件工程

Barry Boehm、Dan Port 和 Kevin Sullivan 提出的 Value-Based Software Engineering（VBSE）主张把利益相关者价值纳入软件的定义、设计、开发、部署与演化。它通过成本、价值和风险回答 “how much is enough”，并把更高价值的设计决策视为软件工程经济学的重要目标。

来源：[Value Based Software Engineering](https://www.nitrd.gov/subcommittee/sdp/vanderbilt/position_papers/barry_boehm_value_based_software.pdf)

### 2. 软件工程经济学

软件工程经济学研究技术选择、成本、时间、风险和收益之间的关系。技术上的完整性只有在特定情境中转化为结果改善时才形成工程价值。设计可变性、形式化方法和架构弹性都需要结合变化概率、收益时点、延迟代价和生命周期成本判断。

VBSE 白皮书把“显著、可衡量地增加软件与 IT 项目随时间创造的价值”列为软件工程经济学路线图的目标，并强调技术机制与价值创造之间的联系。

### 3. 架构成本收益分析

CMU Software Engineering Institute 的 Cost Benefit Analysis Method（CBAM）用于在有限资源下比较架构选项。它综合技术影响、成本、收益、风险和不确定性，从候选变更中选择值得实施的部分。

来源：[Using Economic Considerations to Choose Among Architecture Design Alternatives](https://www.sei.cmu.edu/library/using-economic-considerations-to-choose-among-architecture-design-alternatives/)、[Cost Benefit Analysis Method](https://www.sei.cmu.edu/library/cost-benefit-analysis-method-cbam/)

## 项目操作模型

```text
预期工程净收益 =
  目标效果改善 × 生效可信度 × 受益范围与持续时间
  + 学习价值与未来选择价值
  − 实现成本
  − 维护与认知成本
  − 回归、锁定与机会成本
```

各项含义如下：

| 项目 | 判断内容 |
|---|---|
| 目标效果改善 | 用户结果、系统行为或风险暴露会发生什么可观察变化 |
| 生效可信度 | 因果机制、既有证据和验证结果支持该变化的程度 |
| 受益范围与持续时间 | 当前消费者、复用频率、影响周期和迁移能力 |
| 学习价值 | 本次动作能否消除会改变后续决策的关键不确定性 |
| 未来选择价值 | 是否保留低成本调整、退出或扩展的空间 |
| 实现成本 | 开发、迁移、验证、协调和交付成本 |
| 维护与认知成本 | 长期维护、理解、运行、文档同步和上下文占用；后续读代码、改代码的常是 agent，复杂度、函数与模块规模、CRAP 等可测指标可作为这项成本的代理 |
| 回归与锁定风险 | 正常场景退化、接口固化、迁移困难和供应商依赖 |
| 机会成本 | 本项建设占用资源后被延迟的更高价值工作 |

乘法表达的是约束关系：预计效果很大而生效可信度接近零时，当前预期收益仍然有限。它不要求把定性判断伪装成精确数字。

## 范围选择

实现范围可以是一次局部修改，也可以是跨模块改造。判断对象是整个生命周期中的净价值，范围大小不设先验。

局部修改在问题边界稳定、现有机制可承载、回归面有限时常有较高收益。系统改造在问题重复发生、多个消费者共享能力、局部补丁持续返工或存在统一性硬风险时常有较高收益。

同一项设计的收益会随证据和使用规模变化。当前缺少消费者的检索基础设施可能成本高于收益；当多个场景已经证明动态检索稳定改善结果时，同一基础设施可能成为合理投资。

## 不确定性与验证

不确定性本身进入决策。可逆实验、原型或少量对照样本可以产生信息价值，条件是结果足以改变后续范围选择。

验证动作应回答具体假设：

- 目标问题是否由所判断的机制引起；
- 候选修改是否改善目标结果；
- 改善能否迁移到相邻合法场景；
- 系统性建设是否比复用现有机制带来稳定增益。

不能改变决策的试验、指标和报告没有实质信息收益。

## 在三个开发阶段中的作用

| 阶段 | 工程收益回答的问题 |
|---|---|
| 方案 | 哪个实现范围在当前证据和约束下最值得选择 |
| 实现 | 新发现是否改变原收益假设，是否需要收缩或扩大范围 |
| 审计 | 已实现收益能否覆盖结构、维护和风险成本，后续动作是否值得做 |

方案阶段允许预计收益；实现阶段持续核对关键假设；审计阶段区分已实现收益、预计收益和未证实收益。三者使用同一价值模型，证据强度不同。

## 与常见偏差的关系

| 偏差 | 在收益模型中的表现 |
|---|---|
| 过拟合 | 高估生效可信度或受益范围，忽略相邻场景退化；修复中表现为把所见症状消失当成原因已消除 |
| 过度设计 | 高估远期收益，低估当前实现与维护成本 |
| 过度防御 | 高估兜底带来的局部稳定，低估失败被掩盖后的定位、回归与认知成本 |
| 工程强迫症 | 把文件、抽象、流程、测试数量、指标分数和闭环程度当成结果收益 |

工程收益提供选择目标；这些偏差帮助解释估计为什么失真。诊断偏差仍需要具体证据。

## 使用边界

- 安全、法律、数据完整性和不可逆迁移等硬约束先满足，再比较合规方案的收益。
- 用户明确指定的范围和交付物属于约束，收益判断不能擅自取消或扩展。
- 无数据时保留定性和不确定性，不能编造 ROI、概率或精确分数。
- 工程收益判断只需支撑当前重要决策，不要求建立持续治理、量化平台或额外文档体系。
