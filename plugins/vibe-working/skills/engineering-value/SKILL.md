# 工程收益约束

## 核心原则

在当前证据、资源和授权范围内，选择**完整满足目标、预期工程净收益最高**的可行方案。目标效果、必要质量和明确交付物构成候选资格；缺少这些条件的方案应补全，资源与目标冲突时说明具体冲突并取得取舍。未经授权，不把要求的最终交付降成演示、原型或部分修复。安全、法律、数据完整性和不可逆操作的保护属于硬约束，先满足再比较收益。

工程量是投入，用户结果改善是收益。架构与实现共同接受判断：在能承载问题机制的位置解决问题，保留任务需要的复杂度，计算实现、维护、认知和回归成本。局部修改与系统改造均可成为最佳选择；新功能的已明确使用者也属于直接消费者，无需等待线上失败或第二个消费者出现才设计必要结构。

本 skill 提供决策准则，不提供流程。关键取舍只需给出影响选择的事实和理由；普通改动直接执行。验证、记录、文档和协作步骤同样计算收益与成本，包括用户等待和审阅负担：满足明确要求、改变当前决策或降低实质风险时才增加；正常执行已足以判断的结果就在当场处理。

## 从目标与证据选择方案

区分四类信息：用户要改善的结果、明确约束、观察到的系统事实、待验证的因果假设。用户的场景与输入输出样例是需求证据；其解释和模型自己的推断仍需与实际机制核对。

先澄清对象与口径，再改展示或计算。界面或报表上的症状常源于定义不清：字段的业务含义、统计分母与包含关系、业务对象的归属、"预算""成本"之类的词覆盖哪几类支出。例如两个比例条相互遮挡，改图之前要先确认两类人群是互斥还是包含，分母是否相同；一笔总预算被整体用于一类计算时，要先定义它由哪几类支出构成、各类进入哪条计算路径，再设计输入与补全规则。按比例补全缺省输入是便利，不是最优分配的证明。

方案、任务清单和测试断言中的新增设计继续保留其依据层级：执行要求说明怎样落实，业务必要性由用户目标、使用情境或机制推导支持。提出与执行方案时均核对这条联系，避免用自己新增的验收项反向证明该设计必需。

用户指定的做法不如在问题根源处修复，或难以达成其目标时，指出具体问题，给出更好的方案及两者差异，由用户选择后再实现这一部分；不依赖该选择的工作可以继续。差异不影响目标效果和长期成本时，按指定做法执行。

决定实现位置前，核实会改变选择的事实：相关输入经过哪些执行路径、由哪个组件处理、产生什么输出或副作用；当前运行的是哪个版本，普通目录、worktree、部署目录和容器镜像不是同一版本，先记下提交与改动状态再解释代码。读取相关代码、契约、日志或产物即可支撑的判断直接核实；存在关键歧义时，选择能区分候选原因的检查。只追踪与目标和主要风险有关的路径。

从因果机制与适用条件成立的成熟方法识别方案：第一性推导要说明目标、机制和必要条件，成熟方法要核对适用前提。在确有架构、成本或风险取舍时比较可行替代方案；无需凑方案数量，也无需穷尽所有设计来证明全局最优。

用以下因素组织收益判断，完整解释见按需材料：

| 因素 | 要核实的内容 |
|---|---|
| 目标效果与可信度 | 哪项结果改善；哪些观察、因果关系或成熟实践支持它 |
| 受益范围与持续时间 | 哪些实际或明确计划的消费者受益；问题是否会复现 |
| 学习与未来选择价值 | 哪个关键不确定性会被消除；是否保留调整或退出空间 |
| 全生命周期成本 | 实现、迁移、验证、维护、认知、回归、锁定及被延误工作的成本 |

缺少可靠数字时直接说明依据与不确定性。未来收益须对应有依据的变化情景；方法名称、完整性和可扩展性本身不能证明价值。

## 确定实现边界

新增抽象、schema、基础设施、通用检查器、客户可见章节与交互，或进行跨模块改造时，定位其消费者、保护的结果，以及现有机制不足之处。判断现有内容或能力能否支持消费者的理解、选择与行动，以及新增部分如何改善这些结果；缺少某种形式本身不能证明存在缺口。汇总已有信息若能减少查找、比较或理解成本，也可以形成收益，连同新增阅读与维护负担一起判断。必要配套随目标一并完成；其他优化只有与本次目标直接相关、处于授权范围且净收益明确时才纳入，独立的新目标另行处理。

从模板、可视化或流程完整性推导新增模块，或把方案验收通过当作收益依据时，读 [负例：从展示形式推导需求](references/presentation-scope-case.md) 核对边界。

以下信号帮助确定实现与修复所在的层，不自动决定规模：

- 现有组件已经拥有相应职责、问题因果链直接时，优先在该机制内修正。
- 多个路径共享同一失败原因、分散处理会破坏一致性或持续返工时，修复共同机制并接通相关消费者。
- 即使只有一个消费者，目标要求的恢复、一致性、容量或数据保护也可能需要架构调整；说明必要条件与方案如何满足它。
- 新结构只服务假想复用、命名对称、流程完整或可管理感时，重新评估其收益。
- 标识键要表达真实的归属层级。一个键无法区分"一个任务下多个画布、每个画布多个会话"时，正确登录也会路由到错误会话；一个值同时承担两种身份，例如把历史记录 ID 回填成会话 ID，下游就会把只读记录当作可操作对象。
- 错误类别不合并。限流、额度耗尽、审核拒绝、超时各有恢复动作；适配层丢弃细分错误码、把异步非零错误统一标为不可重试，会把一次短暂限流变成终态失败。成功响应里的空结果同样是失败，不能被软失败吞掉后继续结算。
- 失败处理放在能作出恢复决定的位置；没有有效恢复时让失败可见，并保留定位所需的信息。校验放在外部输入、跨系统接口和持久化数据等信任边界，内部已由契约保证的状态无需层层重复防御。兜底、默认值、重试、兼容层和开关需要实际消费者与可察觉的降级，不用来掩盖尚未定位的原因。
- 一份状态只有一个写入者。两个系统各自写同一状态再靠对账补偿，会出现时序倒挂与撕裂。实时通道与持久状态并存时，终态必须能从持久状态回读，避免漏收一次事件就永久停在"运行中"。

发现关键假设失效时，依据新事实调整方案及受影响实现。更正已经向用户给出的错误判断，说明具体影响；用户语气、先前承诺或已投入工作不能替代事实依据。

## 修复缺陷与样例迁移

报错与代码已能确定原因的直接修复；否则先取得能说明失败的证据：复现、日志，或预期与实际产物的对照。沿相关执行路径找到结果最早偏离预期的位置，以及使失败成立的条件和负责该职责的机制。沿链路逐层核对比逐个试改更快。常见链路：

- 身份与对象：登录身份 → 组织 → 项目 → 任务 → 会话；
- 输入版本：请求引用的是哪份素材或状态；
- 异步执行：接单 → 排队 → 上游任务 → 回调或轮询 → 终态；
- 事件恢复：序号、断线补拉、去重；
- 证据与指标：原始采集 → 去重 → 时间窗 → 分母 → 聚合；
- 资源与费用：模型 → 协议 → 供应商 → 并发槽位 → 计费。

症状相同的两次运行，先比较输入是否相同，再比较返回是否相同，再查缓存与降级记录。候选原因并存时，选择能区分它们的检查；逐个试改代码不能代替定位。

原因所在的层决定修法：

| 原因层 | 典型迹象 | 修法 |
|---|---|---|
| 环境与依赖 | 主机重启后容器未回到业务网络、DNS 解析失败、全部请求在到达上游前失败 | 修依赖与网络，补主机保护；换模型或重试修不了它 |
| 契约与版本 | 节点名、字段别名、弃用接口、文档与实际接口不一致 | 修契约并同步全部消费者；先定位运行的版本 |
| 业务语义 | 口径、作用域、对象归属不清 | 回到定义，再改计算与展示 |
| 上游输入 | 工具抛出看似无关的异常，根源是上游传入空值 | 沿输入 → 节点变量 → 工具入参追到来源 |
| 模型输出 | 格式不合规、未调用工具、输出被截断 | 带解析位置局部纠正，或确定性兜底；不改业务规则 |

修复落在拥有原因的位置。特判、吞错、重试、延时或下游清洗如果只让症状消失，不算修复，除非该位置本身承担这项职责；原因在当前无法修改的外部时，局部缓解需说明针对的原因和残余影响。验证要走集成路径：独立页面或单元测试绕过真实登录、代理与路由时，可能全部通过却遗漏集成缺陷。修复后结合契约、代码或已有案例判断：表面变化后的同类问题得到处理，表面相似但条件不成立的合法情况保持原行为。涉及共享机制或存在难以判断的退化风险时，再用有针对性的运行样例检验；验证投入随失效风险和信息缺口决定。为改动写哪些测试、用什么形态，按 [验证形态选择](references/verification-selection.md)：按任务类型、失败逃逸代价、功能类型和架构边界给出了规则，Codex 按表执行。

同类问题在修复后复现，或新反馈出现在相近位置时，先检查现有修复是否归因错误、作用域过宽或位置失当，再决定修正原修复还是扩展规则。样例中的名称、路径、措辞和固定结果只有属于真实契约时才进入实现。单次要求或临时偏好在其授权范围生效；提升为共享规则需要稳定机制和迁移边界。已观察的定位与修复案例见 [工程观察案例](references/observed-cases.md)。

## 执行、验证与收束

按目标、后果和不确定性选择检查方式。核对实现符合方案的检查与判断用户结果改善的依据各自回答对应问题。证据分级，每级只支持自己的结论：

| 证据 | 支持什么 | 不支持什么 |
|---|---|---|
| 开发者称已修复、代码已提交 | 改动存在 | 已部署、已生效 |
| 流水线成功、测试通过 | 该版本在该环境通过了这些断言 | 真实上游可调用、业务结果正确 |
| 没写实现的一方按需求编写的验收场景通过 | 这些需求场景在该版本成立 | 场景以外的行为 |
| 变异测试杀死率达标 | 现有断言能检出这些代码改动 | 需求场景写全、业务结果正确 |
| 复杂度、函数规模、CRAP 等指标达标 | 结构的后续修改成本在约定范围内 | 设计正确、职责划分合理 |
| 测试环境或候选版本验收 | 该环境下的行为 | 生产已切换 |
| 页面可打开、HTTP 200 | 入口与静态资源可达 | 鉴权后的业务查询成功 |
| 鉴权后接口返回业务数据 | 身份与查询链路通 | 本轮生成或执行已跑通 |
| 本轮独立产物与运行记录 | 这次执行的结果 | 跨条件稳定、效果改善 |

代码不经人逐行阅读时，交付信心来自独立于实现者的证据：验收场景由没写实现的一方按需求编写，变异测试检验断言能否发现行为被改错，复杂度和规模等指标衡量后续 agent 修改这段代码的成本。为通过检查而删改断言、跳过测试、调低阈值或添加屏蔽注释，会让这些证据失去意义，按硬约束处理；指标达标后继续追高分数，例如逐个杀死等价变异体，按收益判断。

测试结果绑定被测版本：记录输入快照与工作树版本，另一处改动后不把旧结果标为对新版本的验证。回合结束不等于交付成功；产物存在、格式有效、关键内容齐全、验收命令通过且绑定正确版本，才是完成。声称运行成功或性能提升须有对应运行结果；"变快了"要报具体计时点，不是报"用了并行"。语义质量可以依据作品与专业判断评估，无需把每项判断量化或另写证明材料。

比较两个方案或两个版本时保证可比：同输入、同配置、同模型；需要随机性的模拟按同一对象配对随机状态，否则差异来自噪声而非方案；不把环境差异或模型差异归因于本次改动。模型对自身工作的评语不是证据，只看产物。

关键收益不确定时，选择可逆且能改变后续选择的验证。失败后利用新证据修正原因、实现或验证方式；相同输入和条件下重复尝试须有新的有效理由。缺少决定性权限、信息或用户价值取舍时，明确所缺内容，并继续不依赖它的已授权工作。

达到本次完成条件、处理了影响交付的缺陷后结束。新增变化、失败或未解决的实质风险可以支撑补充检查；未做与完成条件无关的专项测试不影响交付；确实受阻或尚未确认的关键功能如实说明。

交付用户需要的结果，只说明影响理解或使用的重要变化和未决事项。明确要求或需要追溯时再附检查记录。预计收益与已观察收益分开表述；删去无信息增量的原则复述、承诺与自我评价。

## 审计与相邻技能

审计既有方案时，分开判断已实现收益、预计收益、投入与副作用。缺少收益证据意味着尚未证实；结构无价值需要消费者和失败机制证据支持。四类常见偏差各有表现：过拟合高估可迁移效果；过度设计高估结构净收益；过度防御高估兜底带来的局部稳定、低估掩盖失败后的定位与回归成本；工程强迫症把完整性或过程产物当成收益。定性须指向具体事实，审计建议本身同样接受收益判断。

编写或重构承载实现决策的文档与 skill 时，加载 `rule-skill-authoring` 处理来源、规则和执行链；完整审阅既有 skill 时使用 `skill-audit`。按当前环境支持的方式加载，已加载的指导直接复用。

需要展开收益因素、解释理论依据或追溯来源时，读取 [工程收益理论](references/engineering-value-theory.md)。常规方案与范围判断使用本文件。
