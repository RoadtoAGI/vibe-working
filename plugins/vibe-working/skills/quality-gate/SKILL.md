# 质量闸门

代码不经人逐行阅读时，交付信心来自独立于实现者的可执行证据。闸门依次回答三个问题，前一个不成立时，后一个的测量会随修复而失效：

1. **QA**：行为是否符合需求？
2. **变异测试**：测试能否发现行为被改错？
3. **质量**：结构的后续修改成本是否在约定范围内？

检查深度、范围收缩和发现的处置按 `engineering-value` 判断，开始前加载它。

## 调用

`/quality-gate` 不带参数就是常规用法：审查最近一次交付的全部改动，三阶段级联。可选参数：阶段 `qa` / `mutation` / `quality`（默认 `all`），以及审查范围。单独运行某一阶段时，前置检查照常执行。

- **范围**：起点到当前工作树的全部改动，含未提交和未跟踪的文件。起点由 skill 推断，用户不必给提交号。依次取：本次实现的执行报告或修复单里记下的起点提交；工作树有未提交改动时的 `HEAD`；当前分支与主分支的 merge-base；最近一次与对话中所议任务对应的提交区间（按提交信息里的任务号或主题找）。用户用自然语言描述范围时按描述取，例如"上次 Codex 执行的"、"今天的改动"、"最近三个提交"；给了提交或分支名就直接用。开始时用一行报出推断的范围（起点、文件数），用户不纠正就继续，推断依据写进报告。
- **需求来源**：本次实现所依据的设计文档或计划，从提交信息的 `Source:`、执行报告或对话中的引用找到。没有成文需求时，从对话里的用户要求整理出验收标准，写在报告开头。

## 角色

| 工作 | 由谁做 |
|---|---|
| 写验收场景、分诊存活变异体、处置质量发现、给出结论 | 审查方，即没写这段实现的一方。Codex 写的实现由 Claude 审；Claude 写的实现由用户在 Codex 中调用本 skill |
| 运行检查工具与脚本 | 审查方直接运行；输出长时用 `--json` 或脚本汇总后再读 |
| 补测试、按发现修改实现 | 实现方按修复单执行 |

独立性来自上下文而非模型：审查方没有参与实现的决定，就不会把实现者的误读同时带进代码和测试。审查方与实现方相同时（例如 Claude 审自己直接落地的改动），写验收场景与 LLM 审查交给一个只拿到需求、接口契约和改动文件清单、拿不到实现代码与本次对话的新执行者：Claude 派 subagent，Codex 用 `codex exec` 新会话；无法派发时在报告首行注明同方审查。变异测试与指标是机械测量，不受此影响。

审查方不逐行通读实现。读代码只为三件事：分诊存活变异体、核对超出阈值的函数、确认 LLM 审查提出的问题。

## 项目约束文件

仓库根目录（子工程在其根目录）的 `CONSTRAINTS.md` 记录底线、阈值、检查命令和运行时机。不存在时，第一次运行闸门按 [约束模板](references/constraints-template.md) 生成：先测一次基线，再定初值。阈值是交付约束，只升不降。实现方添加的例外按削弱处理；审查方可以为确有理由的情况添加例外，写明理由与到期日。

## 前置检查

脚本路径以本 skill 目录为基准，各工具的命令见 [工具参考](references/tools.md)。

1. **验收命令**：重跑计划或执行报告中的验收命令，以及 `CONSTRAINTS.md` 中运行时机为"每次交付"的检查，以本次运行结果为准。失败时结论为不通过，修复单先修它，后续阶段不运行。
2. **防削弱**：运行 `scripts/floor_guard.py --base <起点>`。它列出删除断言、新增 skip、新增屏蔽注释、改动阈值配置、改动 `CONSTRAINTS.md`、空异常处理、未实现桩等线索。逐条判断：需求要求删除对应行为、改写后的断言同样严格，属于正常改动；为通过检查而放松的，记为必修项。命中不阻断后续阶段。修复轮重跑时 `--base` 改为修复前的提交，只看修复轮的改动，闸门自己写入的文件不再出现在线索里。

## 阶段一：QA

验收场景从需求和接口契约写出，不参照实现代码，避免把实现者的理解同时写进代码和测试。

- 每条验收标准至少一个 Given / When / Then 场景，并补上需求或契约蕴含的边界与错误路径，例如空输入、权限不足、上游超时、重复提交，只写本次需求涉及的。
- 场景写成项目测试框架中可运行的测试，放进仓库的验收测试目录（没有时按该语言惯例新建，如 `tests/acceptance/`），作为回归测试保留。优先走真实集成路径：绕过登录、代理或路由的测试可能全部通过，却漏掉集成缺陷。
- 夹具、端到端环境等胶水代码工作量大时，审查方写场景和期望值，胶水代码列入修复单交给实现方，并写明断言与期望值必须与场景一致；回收时核对断言没有被改动。
- 用数据表驱动的场景，抽改一个期望值后再运行，测试必须失败；不失败说明这一列数据没有接到断言上。
- 无法自动化的场景（视觉效果、付费外部接口）写成手工步骤并标 `MANUAL`，不用恒真断言代替。

场景失败时判断原因：实现错误列入修复单；场景误读需求就改场景；需求本身有歧义时，按用户目标选定一种解释，写进报告后继续。QA 发现实现错误时，先出修复单；变异与质量阶段留到修复后运行，错误局限于个别函数、其余改动的测量不会因修复失效时，可以这一轮就跑完。

## 阶段二：变异测试

只变异范围内改动过的源文件，排除测试、生成代码、迁移脚本和配置。工具未安装时装进项目的开发环境，新增的依赖与配置写进报告。

- **耗时**：约为变异体数 × 单次测试时长。预计超过一小时时按 `engineering-value` 验证形态选择表的 T1 → T2 → T3 档收缩范围（权限与资金与数据完整性优先，其次业务逻辑，日志与展示最后）；跳过的文件写进报告。长任务放后台运行。
- **分诊**：每个存活或未被测试覆盖的变异体归入一类：
  - **等价**：改动后行为不变，例如只改日志文本、改动不可达分支、类型上下文使两种写法等价。不处理。
  - **测试缺口**：能构造出区分原行为与变异行为的输入。修复单写明该输入、期望输出，以及应补在哪个测试文件。
  - **待定**：无法判断时写明卡在哪里。
- **杀死率**：被杀死数 ÷（总数 − 等价数 − 无法编译或运行的变异体数），与 `CONSTRAINTS.md` 的阈值比较。低于阈值时，按影响从高到低把测试缺口列为必修，直到修完能达标；其余缺口按收益决定。

## 阶段三：质量

**指标**：生成覆盖率文件后运行 `scripts/diff_metrics.py --base <起点> --coverage <文件>`，阈值参数取自 `CONSTRAINTS.md`。它统计改动涉及的每个函数的圈复杂度、行数、覆盖率与 CRAP，以及改动行覆盖率。超出阈值的函数列为必修，`CONSTRAINTS.md` 已登记例外的除外。项目定义了依赖方向或重复度规则时一并检查。

**LLM 审查**：查指标看不到的问题。

- Claude 审查时，有 `code-review` 技能就调用它审查起点以来的改动，档位随风险选择：一般改动用 `medium`，共享机制或数据路径用 `high`；未安装时直接按需求、接口契约和本节结构判据审 `git diff <起点>`。Codex 审查时直接审 `git diff <起点>`。
- 结构问题按 `engineering-value`「确定实现边界」中的信号检查：修复是否落在拥有原因的位置；错误类别是否被合并、失败是否被吞掉；同一份状态是否有两个写入者；标识键能否区分真实的归属层级；新增的抽象、兜底与开关是否有实际消费者。

**处置**：每条发现标"修"或"不修"并附一句理由。修复成本高于收益的不修，例如纯风格问题，或指标已达标后继续提高分数。

## 结论与产出

结论分三档：**通过**；**有条件通过**，只剩不影响行为与数据的低优先级项；**不通过**。

报告与修复单放在本次实现所依据的设计或计划文档同目录的 `collaboration/` 下，按写作方分子目录：Claude 写的进 `claude-code/`，Codex 写的进 `codex/`。文件名为 `YYYY-MM-DD-gate-<topic>-report.md` 与 `YYYY-MM-DD-gate-<topic>-fix-prompt.md`。没有设计或计划文档时，放仓库的 `tmp/quality-gate/`。

- **报告**：范围（起点、终点提交、工作树是否含未提交改动、文件数），测量结果只对这个版本成立；结论；各阶段的数字与可复跑的命令；审查方替需求歧义作出的决定；闸门写入的文件（验收测试、`CONSTRAINTS.md`、工具配置）；未决项。
- **修复单**：交给实现方的执行提示，自含全部约束。每项写目标、涉及文件和验收命令（即当初失败的那条检查），按影响排序；实现方是 Codex 时，写明任务边界、输入、验收命令与报告落盘路径；项目提供 `cc-collaboration-codex` 的 executor 协议时沿用它。闸门写入的文件由实现方在修复轮一并提交。附上底线：不得改动验收场景的断言与期望值，不得修改 `CONSTRAINTS.md`。

通过或有条件通过且没有修复轮时，闸门写入的文件由审查方作为一个提交交付，不留在工作树里。

实现方修完后，只对受影响的文件重跑受影响的阶段。同一项修过两次仍未通过时，先检查修复单本身是否归因错误或要求不清，再决定下一步。
