# 知识到规则与 Skill 工程

规则工程同时处理两个问题。**规则质量**：指导是否成立、清楚、可定位。**规则落实**：指导是否在执行者作决定时进入上下文，并体现在产物中。只有质量没有落实，规则是摆设；只有落实没有质量，执行者会忠实地放大错误。开发时两者一起检查，效果以实际产物判断，不以规则文本的完整程度判断。

本方法适用于 skill，也适用于开发指南、架构说明与协议：消费者是读者和执行者，验收看按文档指导做出的结果。开始时加载 `engineering-value` 决定范围与取舍；创建或大改 skill 时用当前环境可用的 `skill-creator` 处理目录与基础校验；独立审阅由 `skill-audit` 承担并复用本文判据。已加载的内容直接复用。

下文各节是分析动作，不是流程：顺序只受真实依赖约束；普通修改在原规则位置直接完成，不产出台账、字段表或全部阶段产物。

## 核心模型

### 有效规则的五项品质

| 品质 | 含义 | 失效时的典型症状 |
|---|---|---|
| 有源 | 依据可追溯；原始权威、项目设计、用户偏好、待验证假设分开 | 一次经验被写成普遍要求；来源声望代替机制 |
| 有界 | 触发条件、对象、作用域、约束强度与不适用情形明确 | 相邻合法场景被误伤；执行者不知何时停 |
| 有主 | 完整定义只有一个权威位置（SSOT），其他位置只放执行所需的短锚 | 多处定义漂移，改一处漏一处 |
| 可达 | 真实执行者在作相关决定前读到规则、事实和案例；依赖与工具在目标环境可用 | 规则写了没人读；文件存在被当作已加载 |
| 可验 | 有判断规则是否奏效的依据；直接阅读、正常使用或专业判断可以完成验收，专门测试按收益选用 | 只能检查格式，不能判断效果 |

前三项主要决定质量，后两项决定落实。

### 规则原子：一项完整决定

```text
适用时机 → 执行动作 → 验收信号
                ↑
           依据与边界
```

一条规则让执行者知道何时做、做什么、怎样算做到、为什么，以及由谁负责、在哪个范围生效。复合原则拆到执行者能独立判断的决定为止，条件、动作与验收保持相连。

### 理论结合实际

抽象规则给出不变量与判据，实例标出机制成立的条件与适用边界，产物验证两者是否真的改变了行为。三者缺一则失衡：只有理论，执行者按字面表演；只有案例，执行者复制表面形式；没有产物验证，无法知道规则是否进入了决定。理论提出问题与判据，实例提供经过检验的机制，产物回答规则是否奏效；修订从最早失效的一环开始。

来源的效力按类型区分：

| 来源 | 能支持什么 |
|---|---|
| 原始权威 | 在适用范围内成立的领域要求或依据 |
| 项目规则与设计 | 本系统选择的实现、接口与责任关系 |
| 用户要求 | 其授权范围内的目标、偏好和裁决 |
| 既有产物与运行记录 | 观察到的状态和结果，及受证据支持的推断 |
| 工程设计选择 | 有机制理由但仍需验证的做法 |

经验和设计选择要写清依据与适用条件。来源声望、用户情绪和单次成功都不能证明普遍效果。

### 新增先找语义归属

新内容先在现有规则中寻找同一职责、消费者和粒度的位置，原位补充、合并或替换；出现新的决策领域、消费者或生命周期时才调整模块。高内聚来自共同的决策目标，低耦合来自显式依赖与单一权威；文件数量不决定结构质量。

## 规则质量：把知识加工成规则

### 确定权限与交付边界

动手前读取目标目录规则、现有 skill、相关消费者与验证入口，明确本次改变哪些决定、交付什么、获准修改的范围、权威位置与兼容约束。用户目标与事实解释分开处理；缺少关键事实时核实，尚未解决的假设记为 `Open`。

指令冲突按适用的权限层级处理：核对规则的适用条件，判断已有授权是否覆盖拟执行的动作；只有仍需用户裁决的事项才交接，并说明受影响的动作与待决问题。因规则而暂停、请求确认或偏离目标时，给出具体规则文件的链接、关键原句和适用理由，区分[规则的明确要求与执行者的解释][openai-instruction-following]。

对决定权限、范围或存在争议的关键来源，保留定位及其支持的命题；共同依据可以在组级说明，优先复用现有材料。

### 规则原子化与约束强度

提炼或比较规则时，可用 Why / What / When / How（本文简称 WWWH）对齐目的与依据、对象与结果、适用条件、方法与依赖。Why 中区分"为何需要这个结果"与"该方法为何有效"；授权、偏好和接口约定按其权威说明，方法与经验按机制及适用条件说明。这些问题帮助发现关系和遗漏，粒度随当前决策调整，不是固定字段或提问顺序。

存在可独立判断的决定、不同责任方或可分别处理的失败时细化，并保留依赖。约束强度按真实依据选择：

- `hard_constraint`：明确权威要求、事实与因果不变量、必要接口，或不可违反的结果约束。
- `execution_strategy`：有依据的常用执行路径；适用条件变化时可调整。
- `heuristic`：供判断参考的技巧、偏好或经验信号。

**规范约束结果，不约束步骤。** 规则写清交付格式、必要不变量和可观察效果；多种方法都能达到效果时，说明结果应有什么品质，方法留作可选指导。判据：删掉某组步骤后，若仍能从交付物判断规则是否落实，这组步骤就不该成为硬流程。只有下列情形支持固定步骤、顺序、数量、状态字段、重试或独立评审：

- 后一步在事实上依赖前一步，顺序不可交换；
- 流程本身承载授权、安全、隐私、溯源或不可逆操作的约束；
- 外部系统只接受特定的状态转移；
- 只看最终交付物发现不了重大风险，约束过程是当前成本最低的有效控制。

即使流程必要，也只固定依赖、状态和责任边界，不连带固定每一步内部的分析方法。硬门槛和跨责任方交接要写明失败后的动作与责任方；启发式不配状态机。

Schema 不天然内容中立：必填字段、封闭枚举、数量下限和字数门槛都可能把"内容必须以某种形态存在"偷渡进规则。审视字段时问四件事：是否存在不需要它的合格交付？是否存在枚举外的合理实现？数量与效果是否有稳定关系？它有直接消费者，还是只用来证明"做过思考"？没有下游价值的字段设为可选、改为开放描述或删除，不用 `false` / `none` 占位制造表面完整。

同一动作的适用范围在前置读取、执行、验收和交付中保持一致，汇总步骤承接各动作的范围。模型、工具或工作流变化时，复查为旧能力缺口设置的补偿策略：依据失效的原位更新或删除，仍服务其他执行环境或消费者的写明适用条件；权威要求和仍成立的不变量继续维护。[模型适配依据][openai-skills]

### 案例晋升门槛

单次要求与失败先在原始范围处理。提升为共享规则前，提炼去掉名称、路径和表面形式后仍成立的机制，检查它能解释哪些表面不同的同类案例、应排除哪些表面相似的相邻合法案例，再确认现有规则为何不足、哪个位置拥有该职责。

机制或边界不清时，保留局部修复、有范围的设计假设或 `Open`。新增字段、章节、脚本或 skill 需要直接消费者、问题类别或架构推导，以及现有机制不足的依据。修正过的旧表述原位替换。

### 语义规则的案例辅助

规则涉及意图、语境、因果作用、审美或专业判断，字面要求仍容许质量不同的行为时，评估少量示例（few-shot）能否补充判别信息。先排除其他原因：问题来自加载、事实、权威或执行能力时，处理对应原因；重复易错且可确定的判断交给已有程序，新增自动化需有相应收益。

案例的来源是实际观察：真实的决策与产物、用户或领域专家的裁决、获授权的真实作品。模型依规则自行编写的样例不作为来源：它只反映模型对规则的现有理解，可能重复待修正的误读，也不能说明边界在真实任务中成立。提炼时可以删减无关内容、截取片段或脱敏，保留原情境与决定性差异；没有合适观察时保持规则文本，案例缺口记为 `Open`。

用户反馈的正负例按其说明的具体规则归属，保留决定性差异、判定依据与适用边界；有判别信息、适用于当前任务且已有授权时，可以直接作为 few-shot 辅助执行。案例按信息缺口选择类型，不设数量或正负配额。新增、选取、修订或评估运行案例时，读取 [语义案例方法](references/semantic-examples.md)，其中区分案例使用、效果比较与迁移验证，并规定运行提示与留出评测的分离。

### 禁令域先收缩

禁令由有害机制、明确权威或适用的风险策略界定。合法相邻案例被命中时，先修正触发域；旧禁令失去依据则删除，并同步修正编码旧范围的断言。机器无法区分合法与有害情形时，把命中当作复核线索，可靠判据才承担阻断。

开放语义不用词表、禁词或句式配额治理。判断一段内容是否该保留，看它是否改变了状态、信息、关系、风险或选择：删掉后结果是否不变、换序或换角后是否仍成立。这类功能测试能区分合法与有害，词表不能。

非触发案例用于说明范围。只有独立授权或明确状态覆盖同一对象的默认约束时才建立真实例外，写清权威、条件及动作变化。例外数量由事实决定，不按禁令配套豁免，不用文末补丁保留已失效的规则。

### 归并、抽象与职责

围绕当前要改善的决定，比较规则的目标、对象、条件和作用关系，按实际关系选择操作。领域理论可以自上而下指导分组和推导，已有案例可以自下而上帮助发现或修正共同机制：

| 操作 | 依据与结果 |
|---|---|
| 归并 | 相同作用域和消费者职责下，两种表达对触发、要求与允许或禁止的行为、结果、验收、权威边界和强度的规定可双向替代；合为一份权威表达并保留来源 |
| 聚类 | 规则共同支持一项具体决定或组成一段作用机制；按该目标或关系相邻组织，各自保留条件与职责 |
| 抽象 | 提炼能解释成员如何实现目标的共同机制，或跨成员稳定的结果与约束；上位表达保留成立条件，下位规则承载特有条件、非触发边界、真实例外和验收 |

共享目的或主题帮助发现候选；确定关系后再决定归属。一般规则与适用范围更窄的规则是特化关系；共同实现目标的要求是配合关系；分别能实现目标的方法是替代关系；先前结果供后续动作使用是依赖关系。共同部分可以归并，差异留在对应条件或方法中；同一情境下仍冲突的要求按权威与具体取舍处理。

上下层连线应说明实际含义：一般与具体、目标与实现，或前置依赖。同一规则可以被多个任务入口引用，完整定义只在一处维护。关系用自然语言或已有裁决说明即可，关系名称不自动成为工作台字段、枚举或分类配额。

从案例抽象时，先解释哪些关系与条件使目标成立，再判断更换人物、载体或具体手段后哪些关系仍需保留。由理论向下推导时，把原则落实为当前情境中的决定与候选实现。从案例归纳出的可行路径按其依据保留策略性质，其他满足目标与边界的路径继续成立；固定做法的准入沿用"规则原子化与约束强度"。

抽象应能覆盖成员、保留行为差异，并帮助执行者判断或生成新实例。两个有判别力的检查：表面形式改变时，共同关系是否仍适用；关键条件改变时，规则是否相应调整判断。继续概括会丢失这些区别、只剩宽泛目标时，停在能指导决策的条件和机制上。按所需强度使用直接阅读、专业判断或代表性行为检查，形式证明只用于适合形式化的命题。

#### 粒度与模块

一个模块围绕可独立描述的决策目标和交付事务。独立的触发、消费者、生命周期、失败或重试边界共同构成拆分信号；同一事务内的生成、校验和反馈通常保持内聚。跨模块只描述调用条件、输入输出和交接责任，内部实现归各自权威位置。

规则细化到当前执行者能凭可用信息、知识和工具作出所需判断，并理解完成条件。缺少影响决策的条件或能力时，补充指导或接入所需能力；继续细分只会预设执行者已能处理的动作、措辞或思考步骤时停止。上游与下游的分工见"决定空间与交接保真"。

正文直接说明足以自足的操作；同一职责下按条件需要的深度材料进入 reference；需要独立承担任务、并通过输入输出与调用者协作的能力归对应 skill，拆分沿用本节事务边界。篇幅、步骤数和表面复杂度只提供线索，放置与加载遵循下文"SSOT 与渐进披露"。

需要追溯这些方法的研究依据、区分目标与机制或解释跨领域迁移边界时，读取 [归并与抽象的理论依据](references/abstraction-foundations.md)。日常开发使用本节判据即可。

#### 负例：由独立判据直接推出平级类别

2026-09-06，更新 `aigc-writing-guard` 的章节命名规则时，执行者已读取本方法，仍因标题具有独立导航判据而新增第 12 个平级模式，再补上它与低信息密度、抽象评价、模板对称之间的交叉归属说明。用户随后指出高级语义模式仍是扁平散点，要求检查抽象和归并；本例经用户指定记录。

失误发生在结构决策：独立判据支持保留专门条件，平级类别还需要相同抽象层级和独立职责的依据。新增规则前应处理共同机制及其归属。该次实现保留了信息密度兼任原则和诊断、内容保护混入文风问题、修订比较混入原文诊断的结构；读过方法和完成格式校验均未落实这项职责。

修正应落到规则内容：上提跨模式成立的判据，归并等价通则，把保护约束和修订方法放到各自职责位置，子规则保留标题导航等专属条件。只给原列表加分组标题，重复定义和职责混杂仍会留在正文中。

本例用于新增规则时的归属判断。已有归属清楚时原位补充即可；具有独立目标、输入或生命周期的规则可以单列，具体条件和约束强度不同的规则继续保留差异。案例不要求每次修改都重构全库，也不以减少类别数量验收。

## 规则落实：让规则进入执行者的决定

规则写得再好，执行者没读到、读到时决定已经作出、或读到的是转换失真后的版本，产物都不会改变。本节处理规则与产物之间的链路；已观察到的失效形态与修复见 [开发观察案例](references/observed-cases.md)。

### 交付物、上下文与执行循环

用三个执行面定位实际需要的指导。编写者据此选择内容，目标 skill 的流程由任务本身决定：

| 执行面 | 需要时规定什么 |
|---|---|
| 交付物与执行支撑（Harness Engineering） | 用户或下游实际需要的结果、必要工具及使用方式。结果可以是直接答复或作品；另建文件、记录和检查器需有具体消费者 |
| 上下文供给（Context Engineering） | 决策尚缺的信息及取得时机。已取得且仍有效的规则、来源和接口直接复用；缺失、变化或出现疑点时再读取 |
| 执行与反馈（Loop Engineering） | 多步依赖、失败恢复或人机裁决需要的继续、修订、交接与结束条件。一次执行即可完成的任务直接交付 |

来源台账、开发自检、验证分层等开发方法与记录，只有目标运行者确有用途时才进入其工作流或运行包。

每项交付物回答三个问题：承载什么决定、谁消费、如何影响后续决策。无人消费的产物、同一决定的重复表达、把开放语义压成字段的过度结构化，都是删减信号。需要检查时，让检查覆盖实际错误风险，并入撰写或执行中的判断即可；修订只复查受影响内容，跨步骤依赖变化时再更新下游结果和状态。

### 决定空间与交接保真

上游规定必要结果、条件与边界，下游在现场选择实现。上游把具体步骤、措辞或逐项动作写进交付物时，下游会忠实放大它们：产物成为设计的放大器，下游名义上的裁量权形同虚设。判断上游是否越界：删掉这条具体安排、只留结果要求，下游能否凭现场信息作出同样好或更好的选择。

意图、条件和依据经转换与投影后应完整到达消费者。摘要、提取、模板渲染和字段映射不得把目的改写成机械动作，不得把已撤销的旧语义留在当前热路径，不得用内部键名或原始枚举代替消费者能理解的说明。转换器与渲染器就是热路径的一部分；同类断点一次修全，只修一处是打地鼠。

检查者的信息集决定它能看见什么。拿着设计核对产物的检查者，容易把"按设计兑现"当作充分的通过条件；拿不到设计的检查者才能看见"没给就不存在"。两类检查互补而非替代，删减任一侧前先在同一产物、同一轮上比较各自发现了什么。

### 诊断链与修复位置

规则没有体现在产物中时，沿链路定位最早失效的位置，修到对应的责任位置：

```text
来源与案例 → 规则 → 交付与加载 → 执行者决策 → 产物
```

| 失效形态 | 典型迹象 | 修复位置 |
|---|---|---|
| 规则含糊或冲突 | 执行者在矛盾要求之间选了"更保险"的一条 | 规则正文 |
| 信息缺失或失真 | 消费者读到的内容与上游决定不一致；字段有产出无读取 | 生产者、转换器或接口 |
| 加载时机错误 | 参考在决定作出后才到达；旧文件因存在而被读取 | 调度与派发 |
| 执行遗漏 | 规则已到达且适用，动作仍未发生 | 执行者的决策、交接或裁量 |
| 反馈错位 | 问题被发现，却修在症状处而非原因处 | 反馈路由 |

优先改善首次产物。重试、增加检查层、要求执行者复述规则，都不能修复上游问题，只会掩盖它并增加成本。规则强度递增而行为不随之改善时，停止堆叠规则，去查其他环节：加载、输入、能力，或上游已把决定写死。模型对自身遵循的声明不是证据，只看产物。

有失败或未达目标时，定位原因并选择能推进任务的下一步。依据和授权足够时继续工作；必须由用户决定的事项具体交接，权限与规则引起的裁决按"确定权限与交付边界"处理。

### SSOT 与渐进披露

| 内容 | 放置位置 |
|---|---|
| 选取技能所需的触发与边界 | frontmatter `description` |
| 共同目标、高频动作、关键边界、验收与简要依据 | `SKILL.md` |
| 按条件使用的理论、案例方法、完整协议、schema 或排错 | `references/` |
| 可确定计算、重复转换、机械校验 | `scripts/` 或现有测试 |
| 环境支持的 UI、调用策略或 agent 配置 | 对应元配置，如 `agents/openai.yaml` |
| 历史、评审处置与开发证据 | 项目文档或开发产物目录 |

在目标环境实际展示的技能目录中，`description` 以具体任务及边界区分相邻技能；操作细节归正文或按需材料。[描述过长、范围过宽或相互冲突会影响技能选择][openai-skills]。

完整定义只写一次；短锚和按需展开各司其职。热路径按真实加载频率判断：每次必读的 reference 仍是热路径，移到 reference 不等于降低成本。同一机制在热路径重复出现不会提高遵循率，只会分散执行者对其他决定的注意并增加维护点。`SKILL.md` 保持共同决策自足，条件分支有明确的加载指向，分支必需的细节在执行该分支前取得。reference 在具备独立用途和按需消费者时才拆分，少量辅助内容跟随其主用途。正文面向执行者，维护历史和未来路线放到开发记录。

通过**当前宿主规定的加载方式**取得其他 skill 的权威内容：内置 skill 调用、文件读取或资源接口都可能是正式入口。核实内容已进入执行上下文；文件存在与技能名称出现只能证明声明。依赖缺失时按其必要性降级或报告具体阻塞，不虚构工具。

委派任务时提供足以独立执行的目标、约束、输入位置、验收与交接要求。稳定配置由环境元配置或 skill 维护；确认子执行者可达且已取得共享内容后，派发只传任务变量。

## 检查与交付

### 开发期 D1–D6 自检

D1–D6 是开发与独立审阅共用的取证口径，按受影响的规则和执行路径检查：

| 维度 | 判断与处置 |
|---|---|
| **D1 规则僵化** | 启发式、表面特征或开放语义效果被固化为宽泛禁令、固定步骤、阈值或非必要必填。保留有依据的约束，收窄作用域，开放合格方法 |
| **D2 重复冗余** | 同受众、同层、同粒度的正文按决策等价归并为一个 SSOT；特化、配合和替代关系保留差异，短锚与完整展开各按功能维护 |
| **D3 越界** | 他方内部流程回归其责任位置，本模块保留必要调用与交接契约 |
| **D4 权威混写** | 原始依据、项目设计、用户偏好与假设分开；用来源实际支持的命题检查规则 |
| **D5 加载违规** | 偏离宿主正式加载方式、漏读依赖、假定不存在的工具，或把资源存在当作已加载；依目标环境修复 |
| **D6 披露错层** | 高频判据回到决策现场，低频深度按条件供给；按真实加载路径与消费者检查，而非目录名 |

### 验证与交付

证据分三层，每层只支持对应的结论：

| 层 | 证明什么 | 不能证明什么 |
|---|---|---|
| 声明存在 | 文档写了规则、消费者或交接 | 有人读、有人用 |
| 链路存在 | 内容进入了执行上下文，调用与输入输出接通 | 行为因此改变 |
| 效果成立 | 实际决策或产物支持目标效果 | 跨条件稳定，需条件可比的对照 |

按本次变更可能出错的位置选择检查，复用已有适用结果：

| 待判断的问题 | 适用检查 |
|---|---|
| 规则依据、归并或抽象是否成立 | 回看关键来源，按"归并、抽象与职责"比较相关决定与条件，核对归并是否保真、抽象是否能指导实例；清楚的局部修订直接阅读判断 |
| 格式、引用或脚本是否正确 | 相关解析器、链接检查或脚本测试，覆盖受影响部分 |
| 新增或改变的依赖能否接通 | 需要时检查真实加载和调用；已知且未变的接口直接复用 |
| 技能选择或执行行为是否符合预期 | 触发范围变化或出现误调用时，结合实际技能目录检查代表性触发与相邻非触发任务的选择结果；难以判断的语义边界、已发生的执行失败或效果提升主张，检查代表性任务的实际决策与产物 |

行为检查可以复用已收集的负例，观察旧错误是否复发、目标正例行为是否增多；兼顾可能被误伤的合法做法；检查行为本身，不按措辞相似度判分。影响生成行为的高级语义规则至少满足四项：表面方法不同但都满足不变量与目标效果的交付物能同时通过；完整照做推荐步骤却未产生效果的交付物不能因"流程合规"通过；不用任何候选技巧仍实现效果的交付物不因手段缺席失败；内容质量很高但违反事实、权限、安全或接口契约的交付物仍应失败。结构检查通过只说明契约存在。

需要主张泛化或比较版本增益时，使用未展示任务或条件可比的对照：同模型、同配置、同输入；不把模型差异归因于规则改造。

普通修改在内容判断和相关结构检查足够后完成。未开展专项实验不自动使整个 skill 处于待验证状态；能力是否可用、效果是否提升分别按已有依据判断。确实未确认且影响使用的能力如实说明，验证失败则回到对应规则或执行位置修复。

交付用户要求的 skill 或文档，并简要说明重要变化。验证记录、逐项裁决、未决清单或额外报告只在明确要求、协作交接或后果需要追溯时提供。

## 可验证工作台

多来源冲突、规则关系复杂或需要保存裁决证据时，可使用现有等价清单；缺少合适载体再读取 [工作台 Schema](references/workbench-schema.md)，将 [模板](assets/rule-workbench.template.json) 复制到开发产物目录，记录 `sources → rules → clusters → placements → checks`。普通修改不创建工作台。

以本 skill 目录为工作目录执行：

```bash
python3 scripts/validate_rule_workbench.py <rule-workbench.json>
```

实际检查完成且证据可复查后，将 `phase` 设为 `final`，执行：

```bash
python3 scripts/validate_rule_workbench.py --final <rule-workbench.json>
```

该校验器检查工作台结构和所填状态，效果仍需对应输入、执行记录和产物支撑。无法核实的检查保持 `open`；不得仅填入 `pass` 获得完成状态。
